The Stop hook `e2e-gate.py` re-runs `bash .claude/scripts/run-e2e.sh <feature> list` (plus a full-regression pass when `.claude/.vibe-active` is absent) AFTER the agent has stopped — but the orchestrator also asks the agent to tear down every server/container it started. Both can only hold if the E2E run is **self-provisioning**, so F-1 added (runner wiring, no assertion touched):
- `e2e/global-setup.ts` — integration mode only: brings Postgres up, applies the Liquibase changelog, and returns a teardown that runs `down -v` **only if this run started Postgres** (`ps --status running -q postgres` before). Inert when `E2E_MODE=mock`.
- a second `webServer` in `playwright.config.ts` (integration only): `npm --prefix backend run build && npm --prefix backend run start:prod` with `DATABASE_URL=…@localhost:${POSTGRES_PORT ?? 15432}/money_management_test`, readiness URL `/api/v1/me` (Playwright treats 401 as up). `reuseExistingServer: true`, `NODE_ENV` left unset (production would mark the cookie `Secure`, dropped on http).
Result: a cold run takes ~15 s for 22 specs, ~20 s for all 38, leaves no container, volume or listener (verify with `docker ps -a --filter name=money-management`, `docker volume ls --filter name=money-management`, `lsof -nP -iTCP:3000 …`). A harmless `Idle database client failed: terminating connection` backend log appears at teardown.

**The race (found at F-2 Stage 25, fixed in `global-setup.ts`):** `docker compose up -d --wait` does NOT wait for the Liquibase one-shot — it has no healthcheck, so "running" counts as ready. Measured: `up` returned 0.3 s before Liquibase finished, and the very first spec's `signUpViaApi` got `500 relation "users" does not exist` (21/22 on the first cold start; every later request fine). Fix: `up -d --wait postgres` then `compose run --rm -T migrations` (blocks until Liquibase exits; identical to `npm run db:reset`; applies 6 changesets on a fresh DB, 0 on a warm one). Three cold starts passed afterwards.
**How it was proven** (reuse for any "returned too early" doubt): run the command with the Bash tool's `run_in_background`, then compare the output file's sub-second mtime (`stat -f "%Fm" <file>` on macOS; `date -u -r` is whole seconds only) against `docker inspect -f '{{.State.FinishedAt}}' <container>`.

**How to apply:** anything else that starts the stack and calls the API immediately (the Stage 25.5 evaluator recipe, a CI job) must also `run --rm -T migrations` after `up -d --wait postgres`. Later features extend `db-reset.ts` contexts, not this wiring. If a feature needs another real dependency in integration mode, add it to `global-setup.ts`/`webServer` rather than asking the next agent to start it by hand. Never leave a manually started stack running past the Stop — the gate provisions its own; and a stack you leave running makes the next E2E run skip teardown (`wasRunning`) and hides cold-start bugs, so `down -v` before the verifying run. Manual debug stack: `docker compose -f … up -d --wait postgres`, `… run --rm -T migrations`, backend via `run-with-env.sh DATABASE_URL=… -- npm --prefix backend run start:prod` (background, wait with Monitor on `/api/v1/me` → 401), then TaskStop + `down -v`. `docker *` is a sandbox-excluded command, so plain `docker compose …` works from the Bash tool; `npm run db:*` does not.
