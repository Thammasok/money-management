**Rule:** a rule that depends on a Wallet's state at write time ("archived → 409"; later "still a Member", "same Currency") must be ONE statement that also locks the row — `INSERT … SELECT … FROM wallets w WHERE … FOR SHARE OF w RETURNING …` (0 rows = refused; `ledger.repository.ts` → `INSERT_TRANSACTION_INTO_ACTIVE_WALLET`). A lock-free conditional INSERT leaves a window: the archive's `UPDATE` takes `FOR NO KEY UPDATE`, which does not conflict with the insert's foreign-key check (`FOR KEY SHARE`), so an insert whose snapshot predates the archive could commit after it. `FOR SHARE` conflicts with the update's row lock: the insert waits, re-checks the row after the other commit (READ COMMITTED re-evaluation) and finds the change — every stored row commits before the archive. One lock resource per statement means no deadlocks (150 simultaneous renames / archives / recordings: none seen). `FOR SHARE OF w` is accepted inside `INSERT … SELECT`.

**Why it matters later:** F-4 (a removed Member must not slip a Transaction in — put the visibility rule into that same statement), F-5 (an edit that moves a Transaction to another Wallet: not visible 404 → Currency 400 → archived 409, atomically), F-9 (Transfers refuse archived Wallets). Owner-only actions use `WALLET_IS_OWNED`, not `WALLET_IS_VISIBLE` (F-4 widens only the latter). A refused single-statement write returns `null`/0 rows and the **service** classifies 404 vs 409 with a second read (`findOwnedWallet`) — sound while Wallets are never deleted or unarchived.

**Test it deterministically** (`backend/test/support/database.ts`): hold the competing write open on its own connection (`BEGIN; UPDATE …`, no commit), start the repository call, `await waitUntilWaitingForALock(monitorPool, 'INSERT INTO transactions')` (polls `pg_stat_activity` for `wait_event_type = 'Lock'`, 5 s bound), then `COMMIT` / `ROLLBACK` and assert refused / stored. A missing lock shows up as that helper timing out ("never waited for a lock"), not as a flaky assertion. Use a separate monitor pool (the test pool has `max: 2`) and release the held connection in `finally`. At HTTP level: a burst with the competing write in the MIDDLE of the `Promise.all` array; assert invariants (every answer ∈ {201, 409}, stored count = acknowledged count, a later write refused) — never counts that depend on scheduling.

**Time in tests:** `now()` is the transaction START time, so `created_at` / `archived_at` are not a commit-order record (a row can have `created_at` later than the `archived_at` of an archive that committed after it) — assert lock behaviour, not timestamp order. And JS `Date` is milliseconds while Postgres stamps microseconds: "updatedAt moved on" asserted right after creating failed once in a full integration run. Backdate in Arrange (`backdateWallet`: created_at / updated_at − 1 hour) and compare with the re-read baseline.
