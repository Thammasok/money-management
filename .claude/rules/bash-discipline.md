# Bash Discipline — CRITICAL

These rules bind every session in this project — the main/orchestrator session AND all track agents — for any command run (setup, git, docker, tests, one-off checks). Violations break autonomous mode with approval prompts or silent sandbox failures.

A `PreToolUse` hook (`.claude/hooks/bash-lint.py`) — registered in every track agent's frontmatter and in `settings.json` — **enforces** the autonomous-breaking subset of these rules: on a match it blocks the command and returns the fix so the agent self-corrects instead of stalling on an approval prompt. The rules below are the source of truth; the hook is the backstop for when they aren't followed.

- **Never use `cd` in a compound command.** Use absolute paths directly. `cd X && cmd` trips the harness path-resolution guard and forces a manual approval prompt.
- **Never combine `&&` chains with output redirects** (`>`, `2>`, `2>&1`, `2>/dev/null`). The redirect target becomes unanalyzable and prompts for approval.
- **Run one command per call** with full absolute paths. Prefer the dedicated Read/Grep/Glob tools over `cat`/`grep`/`find` in bash.
- **Never use heredocs (`<< EOF`)** — they hang indefinitely in the sandbox waiting for a terminator that never arrives. Create files with the Write tool, then run commands plain.
- **Never pass unquoted globs to bash** (`find …/dir-* -type f`, `ls foo*`) — the harness flags possible glob expansion as unsafe and prompts for approval. Use the Glob tool to discover files and the Read tool to inspect them.
- **Never prefix a command with env vars** (`FOO=1 cmd …`). The prefix shifts the first token off the allow-listed command name (→ approval prompt) and breaks sandbox `excludedCommands` matching (silent sandboxing). Pass env as ARGUMENTS to the allow-listed wrapper instead, so the launch command still starts with the matched script name: `bash .claude/scripts/run-with-env.sh KEY=VAL … -- <command>`. Invoke the wrapper in the **exact relative form** from the project root — never an absolute or `./`-prefixed path (the allow-list matches the literal relative string, same as `run-e2e.sh`); the wrapped command's own args may be absolute.
- **Background long-running commands (servers) with the Bash tool's `run_in_background: true`, never `&` / `$!`** — a trailing `&` plus the `$!` expansion each force an approval prompt. Wait for readiness with the Monitor tool, never a foreground `sleep` (`sleep` is blocked outright in the sandbox).
- **Never use command substitution or backticks** (`$(…)`, `` `…` ``) in a Bash call. The harness can't see what they expand to, so it can't match the allow-list and forces a manual approval prompt ("Contains expansion"). Compute values with the dedicated tools, or move the logic into a script.
- **Never put loops or polling in a Bash call** (`for`, `while`, retry-until-ready). A loop body with a redirect or a `$(seq …)` counter is unanalyzable and prompts; foreground `sleep` is blocked outright. To **wait on a condition**, use the Monitor tool. To **iterate**, move the loop into a `.claude/scripts/*.sh` file invoked by its exact literal relative path and allow-listed in `settings.json` — the analyzer never inspects a script's contents (the `run-e2e.sh` pattern below).
- **Run E2E only via `bash .claude/scripts/run-e2e.sh {feature} list`**, spelled EXACTLY in that relative form from the project root — never with an absolute path, never through `npx`/`pnpm` directly. The sandbox exclusion matches the literal relative string; any other spelling silently re-enters the sandbox and Chromium fails with a Mach-port error. This is the ONE exception to the absolute-paths rule.
- **Never run E2E against a production-mode server** (`USE_PROD_SERVER=1`, `NODE_ENV=production`) — production guards disable dev-only routes and their specs 404 by design.
- **Run a test suite at most once per result you need.** Never re-run the same suite just to see a different slice of output (`| head`, `| tail`) — piped runs killed mid-suite orphan dev servers and browsers. Run it plain once and read the tool output.
- **Running `git` is expected. A `.git` denial means the command is missing from `excludedCommands`, never that git is off-limits.** `git add`, `git commit`, `git merge`, `git fetch`, `git cherry-pick`, and `git push` on a working branch are ordinary commands this harness depends on — `git-flow.md` prescribes the exact sequence, and the main session runs it. The mechanism to know: the sandbox merges `Edit(...)` deny permission rules into its own `filesystem.denyWrite`, and `permissions.deny` carries `Edit(.git/**)` / `Write(.git/**)` to stop you hand-editing refs, `HEAD`, `MERGE_HEAD`, or the index. Merged, those turn a tool-scoped guard into an **OS-level block on `.git` for every sandboxed Bash command**, so a git command that is not in the sandbox `excludedCommands` fails with `fatal: Unable to create '…/.git/index.lock': Operation not permitted` — in ANY repo, including the working directory. The working directory is not the variable; `.git` is denied inside it. The tell is an **asymmetry**: the Edit/Write tools are a separate permission layer, so you may edit ordinary files in that repo — even resolve every conflict — while `git add` is refused. Two consequences follow. First, a **malformed `settings.json` silently disables every setting in it**, exclusions included, so validate that file (`python3 -m json.tool`) before trusting any git denial. Second, **never hand the developer git commands to run on your behalf** — quote the exact error, say which path was refused, and name the missing exclusion. Always blocked regardless of exclusion, because `permissions.deny` is evaluated first in every mode: `git push --force` / `-f` / `--delete` / `--mirror`, pushing to `main` / `master`, `checkout -- `, `restore`, `reset --hard`, `clean`, `filter-branch`, `remote set-url` / `add`, `config --global`.
- **Never use the `gh` CLI for GitHub-side operations** (`gh pr`, `gh issue`, `gh api`, `gh run`, `gh workflow`, `gh repo`, `gh release`, …) — they are deny-listed and the refusal stalls the run. ALWAYS use the **GitHub MCP** tools instead (`create_pull_request`, `get_pull_request`, `list_pull_requests`, `create_issue`, `list_workflow_runs`, …; load them with ToolSearch if not present). The only allowed CLI call is `gh auth status`. If the GitHub MCP is not connected in the session, do not retry `gh` and do not stop the whole run — record the pending operation (e.g. PR title/body) in the track handoff or surface it at the next PAUSE, then continue.
